Software that builds software.

A software factory is not a bigger agent. It is many small agent loops, each with walls around it, fed by a queue of work and drained through gates into production, with people running the whole thing from above.

01 · what is it

The loop is the atom.
The factory is the loop at scale.

The dream of software built on a repeatable, measurable production line goes back to Bob Bemer's 1968 paper "The economics of program production". For fifty years it mostly fell flat, because you can't stamp out ideas the way you stamp out car parts. Coding agents changed that, and the factory is built in three layers.

Loop

One agent, one job, on repeat. Gather context, act, check the result, go again until a condition is met. You stop prompting turn by turn and instead design the small system that prompts the agent for you.

Harness

The walls around a loop. The sandbox it runs in, the tools it can reach, the memory that survives between runs, and the gates that decide what "done" means. Give a raw model no harness and it will spin forever.

Factory

Many harnessed loops at once. A queue of signals goes in: bugs, feedback, requirements. Work is triaged, specced, built, tested, reviewed, secured, shipped and monitored. Monitoring produces new signals, so it never stops.

02 · benefits

Why teams are retooling

Making one engineer faster is no longer the goal. The factory turns the whole delivery lifecycle into a system you can instrument, measure and improve.

24/7

Always-on throughput

Agents work the queue while the team sleeps. Bugs, dependency bumps and migrations stop waiting for a free human.

∑

Compounding learning

Every session, review and incident flows back into the loop. A security finding shapes the next code review.

↻

Workflows as code

Factories are version controlled, so they can be rolled back, canary tested and improved like any other code.

⚖

Model independence

Route each step to the model with the right cost, speed and quality. When models get cheaper, the whole factory gets cheaper.

⌖

Humans move upstream

People spend their time on intent, architecture and specs. Reviewing a 200-line plan replaces a long code review.

▤

Full traceability

Every action leaves a record that traces back to a human-defined intent, which is useful for audits and post-mortems.

⛨

Sovereignty

Run it in the cloud, bring your own key, or run it air-gapped. What the factory learns stays inside your walls.

⇉

Parallelism

One spec can fan out to N agents at once. Throughput is limited by how fast you can verify, not by headcount.

03 · concerns

Generation is a wide mouth.
Verification is the narrow neck.

"The fundamental constraint in a software factory isn't how much code we can churn out: it's how quickly we can verify it."Addy Osmani · Software Factories, Light and Dark
BOTTLENECK

The review queue backs up

Generation keeps growing while human attention doesn't. The real problem isn't volume, it's a surplus of bad PRs passing gates nobody trusts.

COMPREHENSION

Nobody understands the code

If people stop reading the code, they stop understanding the software. Debugging an incident at 3am in code no human has read is a new kind of debt.

TRUST

Built by agents, tested by agents

Stanford CodeX asks who trusts code that agents wrote and agents validated, especially when a security company is the one dropping human review.

DRIFT

Long loops wander off

Dex Horthy's rule of thumb: an agent holds up for 3 to 10 steps and starts losing the thread past 20. Long loops hide mistakes in the corners.

COST

The token bill

"$1,000 in tokens per engineer per day" was meant as a provocation, but it shows that cost has moved from salaries to inference.

HYPE

Vendor-shaped narratives

Much of the writing on this comes from vendors and consultancies. Productivity claims like "3–5x" are mostly unverified.

05 · inner loop + outer loop

Two loops, two clocks

The terms come from the cloud-native era. The inner loop is the edit-run-verify cycle on your machine. The outer loop is everything after you push. Agents are now taking over both, and humans own the loop around them.

Inner loop seconds → minutes

One agent goes through investigate → implement → run → verify, then repeats. It lives in the IDE or CLI. The judge is fast and deterministic: compiler, tests, linter, types. Most AI use so far sits here.

Outer loop hours → days

Issue → PR → CI → review → deploy → observe → new issue. The agents run on their own infrastructure, not your laptop, and are kicked off from Slack, Jira, Linear or GitHub, like Devin and GitHub's Copilot coding agent.

Human loop weeks → quarters

Intent, architecture, policy and deciding which checks earn trust. Osmani's advice: "own the outer loop". Your job becomes designing the loops, not running each turn.

06 · a factory with a complex loop

Watch the line run itself

A real factory is a graph, not a straight pipeline. Forward edges move work ahead, and bounded back edges send it back when a gate says no. An observer agent watches every run and tunes the harness, so the factory gets better at building the more it builds.

Forward edges

signal → triage → spec → plan → build ×3 → test → review → security → ship → monitor.

Bounded back edges

Failed tests go back to build at most 3 times. When retries run out, work goes back to spec, so a retry loop always has a way out.

Outcome routes

A review rejection goes back to spec, a security finding back to build, and a canary rollback back to triage as a new signal.

The loop that edits the loop

The observer scores runs and opens PRs against prompts, skills and model choices, so the failure rate falls as harness quality rises.

06½ · describe the factory as code

Factoryfile: one file, the whole factory

The simulator above is a graph. Factoryfile, an open project by Diego Pacheco, writes that graph down. It is a block format like main.tf, checked like a compiler, that declares factories, agents, stages, forward edges and bounded loops, so any tool can lint, render or run the same factory.

"Stages are the nodes, next lists are the forward edges, and loops are named back edges that stop when until is met or after max passes."Diego Pacheco · Factoryfile
  • One format, five parsers. Python 3.15, a Rust reference, Java 25, Go 1.26 and TypeScript 7 on Bun, all with identical error messages.
  • Two tools. factoryfile-lint (E001–E010, W001–W008) and factory-cli --render · --render-ui.
  • Bounded back edges. loop blocks with until and max, plus exhausted fallbacks, so a retry loop always has a way out.
  • Gates and routes. verdict maps and on routes for passed/failed and yes/no outcomes, plus run stages for test, ship and merge.
  • Eight factories included. XP, RUP, Scrum, Kanban, waterfall, spiral, gated-release, and the repository's own Factoryfile.

07 · self-closed systems

Close the loop, and the system steers itself

An open system needs a human to carry each output back in as the next input. A self-closed system feeds itself: production telemetry becomes new work, results become evals, and evals change the harness. It is control theory applied to an engineering org.

SETPOINT

Intent & specs

What "correct" looks like, written precisely enough for a machine to check. This is the only part humans have to supply.

SENSORS

Telemetry, tests, evals

Deterministic, cheap, frequent and hard to fake. A sensor that drifts or can be gamed makes the loop unstable.

ACTUATORS

Agents with scoped permissions

They change code, config and the harness itself, but only inside the walls the harness allows.

THE CATCH

A closed loop can lock onto the wrong target

If the sensor is wrong, the loop optimizes the wrong thing faster. You need anchors outside the loop: humans setting the setpoint, red-team agents and independent scenarios that the builders never see.

Standardized inputs

Reproducible environments, repo instructions and well-scoped tasks, never "login is broken sometimes".

Deterministic verification

Builds, types, linters, tests and scans give the agent machine-readable evidence that the work is done.

Continuous instrumentation

An execution record of every step, so failures can be replayed and turned into new evals.

Self-improvement

Observer agents score a share of runs and open PRs that adjust prompts, skills and model choice.

08 · lit vs dark factories

Where do you leave the lights on?

The name comes from lights-out manufacturing. At FANUC's plant near Mount Fuji, robots build about 50 robots per 24-hour shift and can run unattended for up to 30 days. In software, a lit factory keeps humans reading at the points where judgment matters. A dark factory lets agents scope, build and ship without anyone reading the details.

🌑 A loop earns the dark when…

  • the check is cheap and runs often
  • the oracle can't be easily faked: green/red tests, type gates, property tests, a review agent with a real rubric
  • the oracle answers immediately and doesn't drift
  • the loop is short (3 to 10 steps)
  • a machine, not just you, can prove "done"

💡 Keep the lights on when…

  • a wrong answer is expensive and only a person can catch it
  • subtle production bugs slip past tests
  • the blast radius is large
  • the decision will shape a year or more of work
  • the main risk is a misunderstood requirement
