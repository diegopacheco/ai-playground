Bug name

Nested jar URLs are parsed again on every cached resource lookup

GitHub · #51503severity lowbranch main @ cf5f3b9espring-projects/spring-boot
2

What the bug is

Every lookup of a resource inside a nested jar builds and parses a java.net.URL, even when the nested JarFile is already cached.

JarUrlConnection.open needs a cache key, not a URL, but it builds the URL first and then derives the key from it.

It then builds a second key in cacheIfAbsent, which on a cache hit only proves the entry is already there.

Nothing is wrong in the output. The cost is allocation and time on a path a starting application walks thousands of times while probing for optional classes and package-info.

Measured on this machine: 480 bytes and 158 ns per warm-cache lookup that could be 192 bytes and 70 ns.

	long id = Thread.currentThread().threadId();
	long before = threads.getThreadAllocatedBytes(id);
	long start = System.nanoTime();
	for (int i = 0; i < MEASURE; i++) {
		JarUrlConnection.open(missing);
	}
	long nanos = System.nanoTime() - start;
	long allocated = threads.getThreadAllocatedBytes(id) - before;

	System.out.printf("allocated %d B/op%n", allocated / MEASURE);
	System.out.printf("time %.1f ns/op%n", (double) nanos / MEASURE);
}

private static void verify(URL present, URL missing) throws Exception {
	if (JarUrlConnection.open(present).getJarEntry() == null) {
		throw new IllegalStateException("cold lookup lost 3.dat");
	}
	if (JarUrlConnection.open(present).getJarEntry() == null) {
		throw new IllegalStateException("warm lookup lost 3.dat");
	}
	try {
		JarUrlConnection.open(missing).getJarEntry();
		throw new IllegalStateException("missing entry was reported as found");
	}
	catch (FileNotFoundException ex) {
		System.out.println("verify ok: cold hit, warm hit, missing entry not found");
	}
}

Unpatched main at cf5f3b9e, three runs: 480 B/op at 157.8, 156.7 and 168.8 ns/op. With the fix below, same harness and same JVM: 192 B/op at 72.3, 70.0 and 75.2 ns/op. This is an allocation assertion, not a wall-clock one: 480 vs 192 bytes is exact and repeats to the byte, while the ns figures carry normal JIT noise.

5

Why this bug is bad

  • It is pure waste on a hot path: the URL that costs the allocation is thrown away as soon as the key is built, on every hit.
  • It scales with how hard a framework probes. Spring probes for optional classes and package-info across every nested jar at startup, so the cost lands where startup time is already scarce.
  • The reporter measured 1.03 GB of allocation on this path shrinking to 205 MB in a real application startup - garbage that the collector has to walk during the worst window for it.
  • Nothing surfaces it. Output is correct, no test fails, and the only symptom is allocation pressure that looks like the class loader being slow.
  • It is worse in memory-tight containers, where the extra garbage per lookup is what pushes a young collection during startup.
6

Minimal solution

Build the cache key straight from the already-parsed nested spec and only construct a URL when the cache misses. One new package-private factory on JarFileUrlKey, one cache read on UrlJarFiles, and the URL work moved inside the miss branch of JarUrlConnection.open. No signature changes, no new fields, no behavior change on a miss.

Breaking change?

No
database schemapublic API / contractbreaks consumers

No schema and no migration - the loader touches no database. All three classes are package-private inside org.springframework.boot.loader.net.protocol.jar, so nothing here is a published signature; the public JarUrl and the JarURLConnection contract are untouched. Callers see the same JarFile for the same URL, the same FileNotFoundException for a missing entry, and the same cache identity, because the new key is equal to the key that a URL would have produced. The one thing to keep honest is that equality: if the nested handler's parsing of protocol, host or port ever changes, the direct key and the URL key would drift, which is exactly what the JarFileUrlKeyTests addition is for.

9

Is the fix safe?

Safe with a caveat

The change is small, local, allocation-only, and reversible by a revert. I compiled unpatched main and the patched tree from the same sources and ran the same harness against both: 480 B/op before, 192 B/op after, with cold hit, warm hit and missing-entry behavior identical on both builds. The caveat is coverage, not design: my harness exercised cold, warm and missing on a synthetic two-entry nested jar. It did not exercise the runtime ref, a signed jar, a multi-release jar, or concurrent cold misses.

Risks

  • forNestedSpec hard-codes what the nested handler produces today (protocol nested, host "", port -1). A change to that parsing would silently split the cache into two keys rather than fail loudly - a memory leak of duplicate JarFiles, not a wrong answer.
  • I could not exercise the runtime ref path: appending #runtime to a nested jar URL in my harness makes the loader look for a nested entry literally named nested.jar#runtime, and it fails that way on unpatched main too. That is a property of my synthetic fixture, not evidence about the fix, and it means the runtime ref branch is unmeasured here.
  • The measurement is one machine, one JVM (Corretto 25.0.2), one tiny nested jar. The direction matches the reporter's JMH numbers on a 168 MB jar; the absolute figures do not transfer.
  • I did not run Spring Boot's own test suite - no Gradle build was executed - so 'existing tests still pass' is not something this triage established.

How to verify

  • ./gradlew :loader:spring-boot-loader:test - the module's 551 loader tests, which this triage did not run.
  • Add the JarFileUrlKeyTests case asserting forNestedSpec(spec, end, runtimeRef) equals new JarFileUrlKey(new URL(spec)) for both ref states; that is the single assertion the whole change rests on.
  • Re-run the allocation harness on both builds and expect the exact byte figures to repeat: 480 B/op unpatched, 192 B/op patched.
  • For the end-to-end claim, take the reporter's route: JFR on a real application startup, and compare sample-weighted allocation on the JarUrlConnection.open path rather than wall-clock startup, which the reporter's own data could not resolve.
