Bug name

A fixed coupon worth more than the cart charges the customer a negative amount

Jira · PIX-482severity criticalbranch mainpixel-cart
2

What the bug is

A $25 fixed coupon on a $15 cart produces a total of -10.

Checkout does not clamp it, so it asks the payment provider for -10.80.

The discount is subtracted from the subtotal with no floor at zero.

Percent coupons never hit this because they can only ever remove 100% of the cart.

Every existing cart test passes, because none of them uses a coupon bigger than the cart.

import assert from 'node:assert/strict'
import { cartTotal } from '../src/cart.mjs'
import { charge } from '../src/checkout.mjs'

const cheapCart = [{ sku: 'MS-9', price: 15, qty: 1 }]
const coupon = { type: 'fixed', value: 25 }

test('a fixed coupon larger than the cart never makes the total negative', () => {
  assert.equal(cartTotal(cheapCart, coupon), 0)
})

test('checkout never charges a negative amount', () => {
  const { amountToCharge } = charge(cheapCart, coupon)
  assert.ok(amountToCharge >= 0, `amountToCharge was ${amountToCharge}`)
})

Both tests fail today: cartTotal returns -10 where 0 is expected, and charge reports amountToCharge was -10.8.

5

Why this bug is bad

  • It moves money the wrong way: a negative charge is a refund, so a coupon can pay the customer out of the merchant's account.
  • It is trivially reachable — any published fixed coupon plus a small cart triggers it, no unusual state needed.
  • The payment provider, not the app, decides what a negative amount means, so the failure mode differs per provider and may not error at all.
  • Ledger rows written from amountToCharge go negative, so revenue reporting is wrong after the fact and has to be reconciled by hand.
  • The test suite stays green while it happens, so nothing alerts anyone.
6

Minimal solution

Clamp the discount to the subtotal in discountFor so a fixed coupon can never remove more than the cart holds. One line, one function, no change to any caller or signature.

+++ b/src/cart.mjs
 export function discountFor(sub, coupon) {
   if (!coupon) return 0
   if (coupon.type === 'percent') return round2(sub * (coupon.value / 100))
-  return round2(coupon.value)
+  return round2(Math.min(coupon.value, sub))
 }
  • Clamping in discountFor and not in cartTotal keeps the reported discount equal to the money actually taken off, so a receipt line cannot disagree with the total.
  • checkout.mjs is left alone: once the total cannot go below zero, the tax line and amountToCharge are correct as written.
  • Negative or malformed coupon values are a separate validation problem and are deliberately not touched here.

Breaking change?

No
database schemapublic API / contractbreaks consumers

No schema, no migration, no signature change. discountFor keeps its arguments and its return type. The only behavior that changes is the case that is already broken: a fixed coupon larger than the cart now stops at the cart value instead of going past it. Any caller relying on a negative total was relying on the bug.

9

Is the fix safe?

Safe

One expression inside one pure function, no state, no I/O, covered by the reproduction test, and undone by a revert. Every existing test keeps passing because they all use coupons smaller than the cart.

Risks

  • Historic orders already written with a negative amount are not corrected by this change and still need a data check.
  • If a caller elsewhere reads discountFor to display a coupon's face value, it now shows the clamped amount, which is the amount actually applied.

How to verify

  • node --test test/repro-negative-total.test.mjs — both tests pass after the change.
  • npm test — the four existing tests stay green.
  • Query orders for amountToCharge < 0 to size the historic damage.
